# Larry 教材 Web 项目

这个结构用于 GitHub 和两台电脑同步维护。

## 目录

- `source/`：Markdown 源文件，后续主要编辑这里。
- `web/`：HTML 查询页面。
- `assets/`：图片素材。
- `docs/`：Word、Excel 等导出文件可放这里。

## 项目分工

本项目采用三层结构：

- Larry 主线：项目的学习顺序和语法判断引擎，HTML 与 Markdown 正文都以它为准。
- 文法俱乐部旁注：作为理论底座、术语来源和细节补强，先做对照，不直接重排 Larry 体系。
- 经济学人实战：在 Codex 对话框中进行句子分析，分析依据是本项目语法体系，不另做网页工作台。

相关索引文件：

- `source/project-method.md`：项目方法论与内容进入规则。
- `source/README.md`：Markdown 源文件导航。
- `source/video-source-index.md`：Larry 视频顺序、BV 号、章节文件和溯源状态。
- `source/evidence-log.md`：已经确认的视频画面、截图和笔记证据记录。
- `source/example-source-audit.md`：例句来源审计表，集中管理已确认和待校准例句。
- `source/update-backlog.md`：后续待补内容和证据需求。
- `source/tense.md`：Larry 时态专题，依据 V19-V22 逐步整理。
- `source/subjunctive.md`：Larry 虚拟语气专题，依据 V24-V26 逐步整理。
- `source/morphology.md`：Larry 词法解析专题，依据 V27-V28 逐步整理。
- `source/grammar-club-crosswalk.md`：Larry 与《文法俱乐部》的章节对照。
- `source/terminology-map.md`：大陆术语与《文法俱乐部》术语对照。
- `source/economist-analysis-protocol.md`：经济学人句子分析输出协议。

## 推荐工作流

1. 修改 `source/*.md`，其中 `source/full-summary.md` 是完整讲义主文本。
2. 若需要网页同步展示，运行 `node scripts/build_web_sections.mjs` 生成 `web/generated-sections.js`。
3. 用浏览器打开 `web/index.html` 查询。
4. 用 GitHub 保存版本历史。

## 展示原则

- 网页中的课程截图不直接使用原始截图，而是重绘成统一风格的信息图。
- 颜色标注使用浅底深字标签，避免纯色文字导致阅读困难。
- HTML 是查询版；Markdown 是源文件；Word/Excel 是导出版。
- 信息图必须先服从 Larry 当前语法体系，再考虑视觉效果：成分功能进入简单句，简单句通过连词形成从句，非谓语 / 不定式与从句可以互相转换理解。
- 后续优化版式时，不能删除或弱化核心关系：名词性 / 形容词性 / 副词性功能、主谓宾定状补、从句 = 连词 + 简单句、非谓语 / 不定式 ↔ 从句。
- 知识结构采用“理解入口 + 类型主表 + 规则补充”的形式：本质、总领描述、独立句变从句等放在入口小节；类型主表只放具体类型；语序、省略、易混点等规则另开补充表。
- 《文法俱乐部》只作为旁注和理论补强进入项目；在 Larry 视频资料未稳定前，不把书中细节大规模写入正文。
- 经济学人文章不整篇保存进项目；只保留必要句子、出处链接、语法分析和学习卡片。
- `The economist/` 这类本地下载资料不进入 GitHub；需要分析时只提取句子和自己的语法分析。
- 知识体系按“例句库工作台 → 语法总览 → 简单句 → 从句 → 非谓语 → 介词短语 → 时态/虚拟/词法 → 易混对比 → 项目说明”组织。
- 每个知识点优先采用“本质 → 判断问题 → 类型表 → 代表例句 → 易混点 → 实战用法”的卡片结构。
- 经济学人实战中反复卡住的句子，回填到对应知识点的例句库、易混对比或判断流程。
- 如果需要调整页面模块、图示结构、知识层级关系等结构性内容，Codex 必须先和我确认，再执行修改。
- Larry 主线内容必须有来源：新增规则标明视频序号和 BV 号；例句只使用视频画面、用户截图或用户上传笔记中的例句，不由 Codex 自行创造。
- 已存在但来源未逐条确认的例句，先登记到 `source/example-source-audit.md`，后续按视频或截图校准，不继续扩写。

## 颜色规则

这是本项目的硬性规则。后续新增内容、网页展示、Markdown 源文件、Word/Excel 导出版，都必须严格按照以下对应关系标注。

- 名词性成分：红色
- 形容词性成分：黄色
- 副词性成分：绿色
- 非谓语 / 不定式：紫色

## 两台电脑维护流程

核心口诀：开工先同步，收工就上传。

### Codex 协作规则

默认情况下，Codex 只负责修改项目文件，不自动提交和推送到 GitHub。

只有当我明确发出以下文字动作时，Codex 才执行 GitHub 相关操作：

- 提交修改
- 提交并推送
- 推送修改

这样可以减少不必要的 token 消耗，也避免在我还没确认内容时自动上传。

### 开始编辑前

文字动作：同步最新版。

含义：把 GitHub 上另一台电脑刚改过的内容，先下载到当前电脑。

### 编辑过程中

文字动作：正常修改文件。

含义：像平时一样修改 Markdown、网页、Word 或资料文件。

### 编辑完成后

文字动作：暂存修改、提交修改、推送修改。

含义：

- 暂存修改：告诉 Git 哪些文件要保存。
- 提交修改：给这次修改起一个名字，形成一个可回退的版本。
- 推送修改：把这次版本上传到 GitHub，让另一台电脑可以同步到。

### 两台电脑轮流使用

1. A 电脑改完：暂存修改 -> 提交修改 -> 推送修改。
2. B 电脑开始改前：同步最新版。
3. B 电脑改完：暂存修改 -> 提交修改 -> 推送修改。
4. A 电脑下次继续前：同步最新版。

不要让两台电脑同时修改同一个文件。尤其是 `web/app.js`、`source/preposition.md` 这类常改文件，最好一台电脑上传后，另一台电脑先同步再继续。
